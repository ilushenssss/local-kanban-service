# Эксплуатация

## Резервные копии

Каталог копий должен находиться вне рабочей папки данных, желательно на другом диске/устройстве. Для копий ограничьте права обычных сотрудников средствами Windows. Кнопка «Резервная копия…» создаёт копию вручную (срок хранения 14 дней).

Для планировщика заданий Windows на сервере или выделенном компьютере с доступом к общей папке:

- Программа: `C:\TeamSync\environment\python\python.exe`
- Аргументы: `"C:\TeamSync\tools\backup.py" "\\server\Общие\TeamSync\data" "D:\TeamSyncBackups" --retention-days 14`
- Рабочий каталог: `C:\TeamSync`
- Расписание: ежедневно, например в 20:00; учётная запись должна иметь доступ к обеим папкам. Для UNC не полагайтесь на подключённые буквы дисков.
- При ненулевом коде выхода проверьте вывод задания; копия без `VERIFIED` не считается успешной. Настройка задания выполняется администратором, приложение не создаёт его автоматически.

На время резервирования удерживается общая блокировка записи, чтение возможно. Большой объём вложений увеличивает время; клиенты могут показать «база занята», после завершения повторите запись. Скрипт проверяет БД, копирует только зарегистрированные вложения и проверяет SHA-256. Результат — каталог `kanban-ДАТА-ID` с `kanban.db`, `attachments/`, `manifest.json`, `VERIFIED`. Только после успеха удаляются отмеченные `VERIFIED` копии старше указанного срока. Неудачные неполные каталоги автоматически не удаляются — их проверяет администратор.

Периодически храните независимую копию резервов; рабочая папка и резерв на одном сервере не защищают от потери сервера.

## Восстановление

1. Закройте приложение у всех сотрудников и остановите задание резервирования.
2. Сохраните весь текущий каталог данных, включая журналы SQLite; не заменяйте его сразу.
3. Выполните через диагностическую консоль или администратором:

```bat
C:\TeamSync\environment\python\python.exe C:\TeamSync\tools\restore.py D:\TeamSyncBackups\kanban-ДАТА-ID D:\TeamSyncRestored
```

Каталог назначения не должен существовать. Скрипт проверяет целостность БД, внешние ключи, соответствие манифеста и хеши всех вложений; при ошибке восстановление не выполняется.

4. Снова проверьте права на восстановленную папку. При закрытых клиентах замените рабочую папку восстановленной или измените `folder` в INI **на всех рабочих местах**. Не допускайте параллельной работы с двумя разными копиями БД.
5. Запустите один клиент, проверьте задачи, историю и открытие вложений, затем разрешите работу остальным. Не копируйте старый `kanban.lock` в восстановленную папку.

Повторная резервная копия после восстановления обязательна. Проверяйте восстановление заранее на отдельной тестовой папке.

## Обновление

1. Закройте все клиенты и остановите резервирование.
2. Старой версией создайте проверенную копию. Сохраните старую программу и её окружение.
3. Замените исходники/окружение новой проверенной поставкой; сохраните `kanban.ini` и рабочие данные. Все рабочие места должны использовать одну версию.
4. Запустите один клиент. Миграции применяются под общей блокировкой; более новая неизвестная схема блокирует запуск старой программы. Текущая схема: версия 1.
5. Проверьте доску, запись задачи, вложения и копию; затем откройте доступ остальным.

Для отката после изменения схемы восстанавливайте согласованную резервную копию данных и старую версию программы вместе. Простая замена Python-файлов назад не является откатом БД.

## Ограничения доступа

Роли и проверка входа по текущему согласованию отсутствуют. Все, кто имеет доступ к данным, могут менять доски и задачи. Неизменяемость истории обеспечена интерфейсом и триггерами SQLite, а не защитой от администратора или пользователя, намеренно меняющего сам файл БД. Не храните в папке данные, требующие разграничения доступа между сотрудниками.
