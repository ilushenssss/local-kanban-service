# Архитектура и данные

Источник требований: запрос пользователя и последующие решения — без ролей, без сервиса, файловая архитектура по образцу ветки pyqt-desktop. Проект самостоятельный; файлы журнала СЗ и его данные не используются. Исходный образец изучен на коммите 62db38c74eacd294885918d80db0874a943c3915.

- `kanban/store.py`: все операции SQLite, файловая блокировка, транзакции, вложения, резервирование.
- `kanban/ui.py`: главное окно и единая форма создания/редактирования, фоновые QRunnable, фильтры, обновление.
- `kanban/widgets.py`: обычные выпадающие списки с отдельным перечнем выбранного, календарь, редактор чек-листа и выбор приоритета.
- `kanban/cards.py`: нативная отрисовка карточек и бейджей приоритетов.
- `kanban/presentation.py`: безопасное читаемое представление старых и новых записей истории.
- `kanban/theme.py`: общие визуальные токены и адаптер QSS.
- `kanban/__main__.py`: конфигурация и запуск.
- `tools/`: подготовка Windows-окружения, резервирование и восстановление.

Рабочая папка: `kanban.db`, `kanban.lock` во время записи, `attachments/<уникальное имя>`. Вложения неизменяемые; удаление вложений в первой версии не предусмотрено. Если процесс завершился между записью файла и транзакцией, может остаться незарегистрированный файл; он не включается в копию. Перед удалением таких файлов нужен отдельный анализ при закрытых клиентах.

## Схема v1

Полный исполняемый SQL — `SCHEMA` в `kanban/store.py`. Миграция 1 идемпотентна; версии фиксируются в `schema_migrations` и `PRAGMA user_version`. Следующие изменения должны добавляться последовательными миграциями под той же эксклюзивной блокировкой, без редактирования уже выпущенной схемы.

| Таблица | Назначение и ограничения |
|---|---|
| users | уникальный login, display_name; имя Windows, без паролей |
| boards | название, архивирование, created_at |
| board_members | зарезервирована для будущих ролей; сейчас не используется |
| columns | FK board_id, имя, порядок, is_done, необязательный положительный wip_limit |
| tasks | составной FK column_id+board_id, уникальные board_id+number, непустое название, текст, приоритет, срок, порядок, UTC-даты, архивирование, version |
| task_assignees | составной PK task_id+user_id и FK |
| labels | метки доски, уникальные board_id+name |
| task_labels | составной PK task_id+label_id и FK |
| checklist_items | task_id, текст, done, порядок |
| comments | task_id, автор, текст, created_at |
| attachments | task_id, автор, исходное имя, уникальный stored_name, размер, sha256, created_at |
| task_history | task_id, автор, UTC-время, операция, JSON прежних/новых значений; UPDATE/DELETE запрещены триггерами |
| settings | ключ–значение для дальнейших общих настроек |
| schema_migrations | версия и время применения |
| request_deduplication | UUID операции, тип, отпечаток запроса, сохранённый результат |

Индексы: доска/архив/колонка/порядок, сроки, история/комментарии/вложения задачи, обратные связи исполнителей и меток. Связи задач с метками создаёт единый слой хранения только внутри доски. Физическое удаление задач/досок не реализовано; используется архивирование. Порядок карточек задаётся числовой позицией между соседями, равные позиции упорядочиваются по ID.

## Транзакции

Каждая запись: получить lock атомарным созданием → BEGIN IMMEDIATE → проверить UUID повтора → проверить версию и принадлежность доске → изменить данные и историю → сохранить результат операции → COMMIT → снять собственный lock. Проверка версии предотвращает потерю изменений задачи; настройка колонок проверяет полный набор их ID. Согласование одновременного переименования доски/колонок по версии отдельно не реализовано — последнее сохранение этих настроек побеждает.

Задачи после перемещения в завершающую колонку получают completed_at; после возврата дата очищается. Переназначение завершающей колонки тоже меняет состояние задач, увеличивает версии и создаёт историю. Комментарии и вложения добавляются независимо и не перезаписывают редактируемые поля задачи.

Фильтры выполняются SQL по всему набору задач. Детальная задача и результат выборки читаются в транзакции-снимке. Отдельные обновления досок и колонок могут попасть в разные снимки; следующая синхронизация исправляет представление.

## Проверка условий эксплуатации

Поддерживаются единицы и десятки пользователей; фактическая пропускная способность зависит от SMB и размера вложений. Требуется пилотная проверка на выбранной сетевой папке: два Windows-клиента, параллельные изменения, отключение сети, повтор записи, восстановление. Локальные многопроцессные тесты не заменяют эту проверку.


## Справочники версии 1.1

Используются уже существующие `users` и `labels`: схема остаётся v1, данные не пересоздаются. `Store.catalogs()` читает справочники в одном снимке; `save_user()` добавляет сотрудника или меняет display_name при неизменном login; `add_label()` добавляет метку доски и не дублирует существующую. Все записи защищены теми же блокировкой, транзакцией и UUID повтора. Пользователь Windows автоматически регистрируется как раньше; пароль и роли не добавляются. Удаление сотрудников и меток не предусмотрено, чтобы не терять ссылки в старых задачах.

Задача хранит связи с ID пользователей и меток, UI выбирает исполнителей/метки из справочников. Дополнительное поле assignee_names в результате чтения используется только для отображения. История в БД остаётся исходным JSON и неизменяемой; UI безопасно экранирует содержимое и показывает русские названия полей, имена колонок/сотрудников и даты. Изменение имён в справочнике не переписывает сохранённые события. При отображении старых событий имена разрешаются по текущему справочнику.


## Исправление выбора и тема 1.1.1

Вместо checkable-модели QComboBox используется RegistrySelection: обычный QComboBox с сигналом activated добавляет выбранное значение, QListWidget показывает назначения/метки, кнопка «Убрать» снимает связь. На время заполнения блокируются сигналы только самого combo, а не структурные сигналы модели. Дубликаты не предлагаются; после удаления значение снова доступно. Фоновое обновление не пересоздаёт список, если справочник не изменился.

DateField использует компактный стандартный QDateEdit, как в эталоне: dd.MM.yyyy, календарь по стрелке, ширина 160. Отдельного флажка включения нет. Необязательный срок обозначается «Без срока», очищается ссылкой «Сбросить»; пустой календарь открывается на текущем месяце без назначения даты при отмене.

В kanban/theme.py REFERENCE_STYLE — неизменённая STYLE из sz/ui/common.py эталонной ветки на коммите 62db38c74eacd294885918d80db0874a943c3915. KANBAN_STYLE распространяет её на текстовые поля и специфичные поверхности TeamSync; стрелки, календарь и полосы прокрутки рисует стандартный Fusion, как в эталоне. Данные и схема не менялись.

## Непрочитанные и виды 1.6

Схема остаётся v1. Персональные отметки чтения используют settings: ключ `read:` + JSON [login, task_id], значение — последний увиденный ID комментария. Store.mark_read проверяет принадлежность сообщения задаче и монотонно повышает отметку транзакционно. Отметки не меняют версию/историю задачи. detail_in возвращает unread_count для текущего Store.login, исключая собственные комментарии. Копии БД сохраняют и отметки. Пользователь идентифицируется прежним Windows login, авторизация/роли по-прежнему отсутствуют.

board_views.py предоставляет список и диаграмму существующих дат. Дерево досок не создаёт новую модель проектов. Веб-сервис не добавлен: пользователь подтвердил сохранение PyQt5. Все обращения к Store из UI идут через Async.

## Схема v2 — общий чат (TeamSync 2.1)

Миграция 2 под прежней эксклюзивной блокировкой и транзакцией добавляет `team_messages(id PRIMARY KEY, user_id REFERENCES users(id), body, created_at)`. Существующие задачи не меняются. `PRAGMA user_version=2`, запись в schema_migrations. Старые программы со схемой v1 отказываются открывать новую БД: обновить необходимо все рабочие места.

Отметки прочтения общего чата хранятся отдельно в settings под `team_read:<login>`, монотонно повышаются до реально загруженного и видимого сообщения. Отправка использует request_deduplication и стабильный UUID. Чтение — транзакционный снимок, после первого получения UI запрашивает только сообщения с большим ID. Бейдж не включает собственные сообщения. Весь чат общий, без новой системы входа и без личных каналов. Backup/restore сохраняет сообщения вместе с SQLite и отдельно вложения прежних задач.

## Схема v4 — фотостикеры

team_messages.kind различает text и sticker (старые записи мигрируют в text). team_stickers привязывает к сообщению имя файла, SHA-256, размер и размеры изображения. Файлы хранятся в attachments/ с отдельным префиксом team-; имя выводится из login и request UUID, исходные имена не используются. Store повторно проверяет формат/размер и нормализует вход в статический PNG через kanban/stickers.py, пишет временный файл, fsync и os.replace до транзакционного добавления сообщения. При неопределённом commit повтор с тем же UUID возвращает прежнее сообщение; изменённое содержимое запрещено. После отката возможен неиспользуемый файл, но сообщение на частичный файл не ссылается. Загрузчик проверяет размер и SHA-256. Backup и restore включают обе разновидности вложений; restore сохраняет поддержку старых копий без team_stickers.

В лёгкую ветку включён официальный Qt 5.15.2 x64 WebP-плагин с лицензиями: kanban/qt_plugins/README.md. Сборка нового окружения сохраняет qwebp.dll. Новых Python-зависимостей и сетевых загрузок при запуске нет.

## Фоновые уведомления и орфография

Notifications получает только новые записи из успешного Messenger.poll, независимо от видимости окна. В памяти хранятся ID последнего увиденного сообщения и короткая очередь уведомления. Первый опрос исключает старую историю; повторные ответы не дают повторных уведомлений. Канонический источник непрочитанных остаётся в Store. QSystemTrayIcon использует пользовательский рабочий стол, отдельная служба и сетевой API не вводятся.

Орфография не изменяет модель данных. Spylls 0.1.7 поставляется исходниками в kanban/_vendor/spylls, русские и английские словари — в kanban/dictionaries. Метаданные источников и хеши закреплены в SOURCES.json/README. Чтение словарей идёт в фоне, проверки слов используют ограниченный LRU-кеш; обращения к сети отсутствуют. Новых DLL/Python-модулей в environment не требуется. При ошибке загрузки словаря редактирование остаётся доступным, ошибка записывается в журнал. Схема данных остаётся v4.

## Схема v5 — чаты досок и изменение меток

team_messages.board_id с внешним ключом boards и индексом (board_id,id) разделяет текст и стикеры по доскам. Старые записи транзакционно переносятся на активную «С-А» (или новая доска этого имени создаётся с владельцем-администратором). Существующие ID сообщений и файлы стикеров сохраняются; team_read отметки копируются в board_read:[login,board_id]. Ошибка неоднозначного назначения откатывает миграцию. Старые ключи settings остаются для истории.

Store.team_chat/team_send/team_send_sticker/team_mark_read принимают board_id; UI всегда передаёт его явно. Неявное значение разрешается только при единственной доступной доске. Авторизация повторяется внутри транзакции записи, а UUID привязан к доске через payload. team_sticker определяет доску по сообщению и проверяет доступ перед чтением файла. chat_updates возвращает только сообщения активных доступных досок для фоновых уведомлений.

retired_labels(board_id,name) блокирует неявное восстановление удалённых/переименованных меток из старых новых задач. Явный add_label разрешает создание заново. label_sequence не допускает повторного использования ID после удаления. edit_label сохраняет ID при переименовании, удаляет task_labels перед удалением labels и увеличивает версии/историю всех затронутых задач, включая архивные. expected_name защищает от устаревшего редактора, request_id — от двойной записи.

## Схема v6 — личные доски

boards.personal — NOT NULL boolean с DEFAULT 0 и CHECK, прежние доски мигрируют как рабочие. owner_id личной доски всегда назначается текущему uid при создании; client payload не выбирает владельца. Изменение общей роли не требует передачи личных досок и не меняет их владение. Перенос между рабочим и личным типом не реализован.

Store.require проверяет личное владение до административного bypass. Владелец имеет read/edit/manage/create_task/archive_task независимо от роли. board_visibility задаёт единое SQL-условие для списка досок, неявного выбора единственной доски чата и chat_updates. Для личной доски membership и роль admin не открывают доступ; остальные чтения/записи проходят через require. catalogs возвращает только владельца в качестве исполнителя, save_task запрещает назначать другого пользователя, включая администратора. board_access/set_board_access запрещены и для владельца личной доски. Проверка записей выполняется в прежней транзакции и до возврата дедуплицированного результата.

archived_personal_boards возвращает только свои личные доски; restore_personal_board повторно проверяет manage и personal перед восстановлением. UUID сохраняет безопасность повторов. Файловая архитектура и резервирование прежние: приватность относится к штатному приложению, не к прямому доступу к SQLite/attachments. Административная резервная копия сохраняет и личные доски с прежним owner_id.

## Схема v7 — события задач для уведомлений

task_notifications(id,history_id,user_id,UNIQUE(history_id,user_id)) хранит получателей события со ссылкой на неизменяемую task_history. Индекс (user_id,id) обслуживает фоновое чтение. Store.history добавляет получателей в той же транзакции, что и изменение задачи: текущие исполнители, создатель из первого события «Создание», прежние исполнители из изменения assignees. Автор текущей операции исключается. Пустой changes и один position не создают уведомления. Повтор UUID возвращает прежний результат до повторной записи истории; откат удаляет и историю, и уведомления.

task_updates(None) возвращает начальный глобальный ID без событий. Последующие чтения ограничены user_id и board_visibility, исключают собственные действия и архивные доски. Глобальный курсор берётся в том же read snapshot; событие, записанное после снимка, попадёт в следующий опрос. Получатели фиксируются в момент записи, поэтому снятый исполнитель не теряет само событие снятия, но отзыв доступа к доске всё равно закрывает его. Новая миграция не создаёт уведомления задним числом из прежней истории; роли/личные доски и старые данные сохраняются.

Notifications читает чат и события задач в существующем worker; отдельные курсоры/очереди сохраняют независимость настроек. Перед системным показом в worker повторно проверяются detail/active_board, при клике карточка снова читается через Store. Обычное административное резервирование включает новую таблицу вместе со всей SQLite-базой. Новых библиотек или службы нет.

## Непрочитанные события досок без изменения схемы

Store.board_badges читает один транзакционный снимок и возвращает chat/tasks/total для активных доступных досок. Чат использует существующие board_read:[login,board_id]. Задачи агрегируются из task_notifications для текущего uid с тем же board_visibility и исключением собственных действий. settings с ключом task_notice_read:<uid>:<task_id> хранит максимальный подтверждённый ID уведомления задачи. Схема остаётся v7, отдельная миграция не требуется.

detail_in возвращает notification_cursor и notification_read без автоматического подтверждения. mark_task_notifications_read проверяет доступ, принадлежность ID пользователю и задаче, монотонно повышает маркер под прежней write-блокировкой. Поэтому ответ более старого окна не помечает последующие события прочитанными. task_updates исключает уже прочитанные записи, а flush_tasks повторно проверяет notification_read перед системным показом. Маркеры входят в обычное резервирование/восстановление вместе с settings.
