# Архитектура и данные

Источник требований: запрос пользователя и последующие решения — без ролей, без сервиса, файловая архитектура по образцу ветки pyqt-desktop. Проект самостоятельный; файлы журнала СЗ и его данные не используются. Исходный образец изучен на коммите 62db38c74eacd294885918d80db0874a943c3915.

- `kanban/store.py`: все операции SQLite, файловая блокировка, транзакции, вложения, резервирование.
- `kanban/ui.py`: главное окно и единая форма создания/редактирования, фоновые QRunnable, фильтры, обновление.
- `kanban/widgets.py`: обычные выпадающие списки с отдельным перечнем выбранного, календарь, редактор чек-листа и выбор приоритета.
- `kanban/cards.py`: нативная отрисовка карточек и бейджей приоритетов.
- `kanban/presentation.py`: безопасное читаемое представление старых и новых записей истории.
- `kanban/theme.py`: общие визуальные токены и адаптер QSS.
- `kanban/__main__.py`: конфигурация и запуск.
- `tools/`: подготовка Windows-окружения, резервирование и восстановление.

Рабочая папка: `kanban.db`, `kanban.lock` во время записи, `attachments/<уникальное имя>`. Вложения неизменяемые; удаление вложений в первой версии не предусмотрено. Если процесс завершился между записью файла и транзакцией, может остаться незарегистрированный файл; он не включается в копию. Перед удалением таких файлов нужен отдельный анализ при закрытых клиентах.

## Схема v1

Полный исполняемый SQL — `SCHEMA` в `kanban/store.py`. Миграция 1 идемпотентна; версии фиксируются в `schema_migrations` и `PRAGMA user_version`. Следующие изменения должны добавляться последовательными миграциями под той же эксклюзивной блокировкой, без редактирования уже выпущенной схемы.

| Таблица | Назначение и ограничения |
|---|---|
| users | уникальный login, display_name; имя Windows, без паролей |
| boards | название, архивирование, created_at |
| board_members | зарезервирована для будущих ролей; сейчас не используется |
| columns | FK board_id, имя, порядок, is_done, необязательный положительный wip_limit |
| tasks | составной FK column_id+board_id, уникальные board_id+number, непустое название, текст, приоритет, срок, порядок, UTC-даты, архивирование, version |
| task_assignees | составной PK task_id+user_id и FK |
| labels | метки доски, уникальные board_id+name |
| task_labels | составной PK task_id+label_id и FK |
| checklist_items | task_id, текст, done, порядок |
| comments | task_id, автор, текст, created_at |
| attachments | task_id, автор, исходное имя, уникальный stored_name, размер, sha256, created_at |
| task_history | task_id, автор, UTC-время, операция, JSON прежних/новых значений; UPDATE/DELETE запрещены триггерами |
| settings | ключ–значение для дальнейших общих настроек |
| schema_migrations | версия и время применения |
| request_deduplication | UUID операции, тип, отпечаток запроса, сохранённый результат |

Индексы: доска/архив/колонка/порядок, сроки, история/комментарии/вложения задачи, обратные связи исполнителей и меток. Связи задач с метками создаёт единый слой хранения только внутри доски. Физическое удаление задач/досок не реализовано; используется архивирование. Порядок карточек задаётся числовой позицией между соседями, равные позиции упорядочиваются по ID.

## Транзакции

Каждая запись: получить lock атомарным созданием → BEGIN IMMEDIATE → проверить UUID повтора → проверить версию и принадлежность доске → изменить данные и историю → сохранить результат операции → COMMIT → снять собственный lock. Проверка версии предотвращает потерю изменений задачи; настройка колонок проверяет полный набор их ID. Согласование одновременного переименования доски/колонок по версии отдельно не реализовано — последнее сохранение этих настроек побеждает.

Задачи после перемещения в завершающую колонку получают completed_at; после возврата дата очищается. Переназначение завершающей колонки тоже меняет состояние задач, увеличивает версии и создаёт историю. Комментарии и вложения добавляются независимо и не перезаписывают редактируемые поля задачи.

Фильтры выполняются SQL по всему набору задач. Детальная задача и результат выборки читаются в транзакции-снимке. Отдельные обновления досок и колонок могут попасть в разные снимки; следующая синхронизация исправляет представление.

## Проверка условий эксплуатации

Поддерживаются единицы и десятки пользователей; фактическая пропускная способность зависит от SMB и размера вложений. Требуется пилотная проверка на выбранной сетевой папке: два Windows-клиента, параллельные изменения, отключение сети, повтор записи, восстановление. Локальные многопроцессные тесты не заменяют эту проверку.


## Справочники версии 1.1

Используются уже существующие `users` и `labels`: схема остаётся v1, данные не пересоздаются. `Store.catalogs()` читает справочники в одном снимке; `save_user()` добавляет сотрудника или меняет display_name при неизменном login; `add_label()` добавляет метку доски и не дублирует существующую. Все записи защищены теми же блокировкой, транзакцией и UUID повтора. Пользователь Windows автоматически регистрируется как раньше; пароль и роли не добавляются. Удаление сотрудников и меток не предусмотрено, чтобы не терять ссылки в старых задачах.

Задача хранит связи с ID пользователей и меток, UI выбирает исполнителей/метки из справочников. Дополнительное поле assignee_names в результате чтения используется только для отображения. История в БД остаётся исходным JSON и неизменяемой; UI безопасно экранирует содержимое и показывает русские названия полей, имена колонок/сотрудников и даты. Изменение имён в справочнике не переписывает сохранённые события. При отображении старых событий имена разрешаются по текущему справочнику.


## Исправление выбора и тема 1.1.1

Вместо checkable-модели QComboBox используется RegistrySelection: обычный QComboBox с сигналом activated добавляет выбранное значение, QListWidget показывает назначения/метки, кнопка «Убрать» снимает связь. На время заполнения блокируются сигналы только самого combo, а не структурные сигналы модели. Дубликаты не предлагаются; после удаления значение снова доступно. Фоновое обновление не пересоздаёт список, если справочник не изменился.

DateField использует компактный стандартный QDateEdit, как в эталоне: dd.MM.yyyy, календарь по стрелке, ширина 160. Отдельного флажка включения нет. Необязательный срок обозначается «Без срока», очищается ссылкой «Сбросить»; пустой календарь открывается на текущем месяце без назначения даты при отмене.

В kanban/theme.py REFERENCE_STYLE — неизменённая STYLE из sz/ui/common.py эталонной ветки на коммите 62db38c74eacd294885918d80db0874a943c3915. KANBAN_STYLE распространяет её на текстовые поля и специфичные поверхности TeamSync; стрелки, календарь и полосы прокрутки рисует стандартный Fusion, как в эталоне. Данные и схема не менялись.

## Непрочитанные и виды 1.6

Схема остаётся v1. Персональные отметки чтения используют settings: ключ `read:` + JSON [login, task_id], значение — последний увиденный ID комментария. Store.mark_read проверяет принадлежность сообщения задаче и монотонно повышает отметку транзакционно. Отметки не меняют версию/историю задачи. detail_in возвращает unread_count для текущего Store.login, исключая собственные комментарии. Копии БД сохраняют и отметки. Пользователь идентифицируется прежним Windows login, авторизация/роли по-прежнему отсутствуют.

board_views.py предоставляет список и диаграмму существующих дат. Дерево досок не создаёт новую модель проектов. Веб-сервис не добавлен: пользователь подтвердил сохранение PyQt5. Все обращения к Store из UI идут через Async.
