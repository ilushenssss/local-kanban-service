# Роли и установка администратора (схема v3)

Приложение по-прежнему открывает SQLite и вложения напрямую. Права проверяются в Store и интерфейсе; пользователь с доступом к файлам может обойти их вне приложения. Для защиты от такого обхода необходим отдельный серверный API. Общая Windows-учётная запись означает одного пользователя приложения. Текущая идентификация сохранена: `getpass.getuser()`, без паролей и SID; одноимённые локальные аккаунты не различаются.

## Права

- Администратор ровно один: все доски, сотрудники, роли, доступ, колонки, метки, резервирование. При передаче роли предыдущий администратор становится менеджером. Снять роль с единственного администратора без передачи нельзя; уникальность администратора также защищена индексом БД.
- Менеджер создаёт доски и задачи, меняет задачи на доступных досках. Управляет участниками, названием, колонками и метками только собственных досок. На любой доступной доске может архивировать и восстанавливать задачи. Владельца доски меняет администратор.
- Сотрудник видит доступные доски и меняет существующие задачи: название, описание, приоритет, срок, исполнителей, чек-лист, колонку/положение. Создание и архивирование задач запрещено.
- Все пользователи доступной доски читают историю, пишут комментарии, добавляют и скачивают вложения. Исполнители выбираются среди участников, владельца и администратора. Новая метка требует управления доской.
- Общий чат доступен всем зарегистрированным пользователям и не привязан к доскам. Новый пользователь при первом запуске регистрируется как сотрудник, без доступа к доскам.

## Обновление существующей установки

1. Закройте все клиенты и сохраните полную копию рабочей папки данных: `kanban.db` и `attachments/`. Не копируйте работающую базу. Сохраните `kanban.ini` и `environment/`.
2. Обновите файлы программы из ветки updates на всех рабочих местах. В ней нет встроенного Python. Старые клиенты не поддерживают схему v3 и откажутся открывать обновлённую базу.
3. Узнайте точный логин будущего администратора **на том компьютере и под той учётной записью, где он запускает приложение**. В cmd из папки программы:

   ```bat
   environment\python\python.exe -c "import getpass; print(getpass.getuser())"
   ```

   Используйте напечатанное значение, например `ivanov`. В текущей модели не добавляйте `DOMAIN\`, если команда его не напечатала.
4. На сервере в cmd перейдите в папку обновлённой программы и выполните (пути замените своими):

   ```bat
   cd /d "D:\TeamSync"
   environment\python\python.exe tools\init_admin.py --data "D:\TeamSync\data" --account "ivanov"
   ```

   `--data` указывает на папку с **действующей** `kanban.db`, указанную в `kanban.ini`, а не обязательно на соседнюю `data`. Скрипт отказывается работать, если база отсутствует. Он мигрирует существующую базу и назначает администратора; прежние ID пользователей, задачи, сообщения, история и вложения сохраняются. Повторное назначение через скрипт запрещено.
5. Администратор запускает приложение обычным ярлыком. В «Настройки → Роли сотрудников» назначает менеджеров. В «Настройки → Участники доски» выбирает владельца и отмечает пользователей с доступом, затем сохраняет.

После миграции прежние пользователи становятся сотрудниками; старые записи членства сохраняются. Ранее таблица членства не использовалась: обычно она пуста. До настройки доступа старые доски доступны только администратору; он получает владение всеми досками без владельца. Доступ не выдаётся автоматически по назначению исполнителем. Сначала восстановите доступ прежним исполнителям, затем продолжайте работу с задачами.

Новую пустую установку сначала запустите один раз, чтобы создать базу, затем закройте и выполните назначение администратора той же командой. До назначения администратора операции приложения запрещены, сообщение указывает на `init_admin.py`.

## Передача администратора

Текущий администратор открывает «Настройки → Роли сотрудников», выбирает другого сотрудника, роль «Администратор» и подтверждает. Передача выполняется одной транзакцией. Старый администратор остаётся менеджером и сохраняет свои доски. Существующие владельцы не меняются автоматически.

После отзыва доступа открытая карточка больше не может читать/сохранять данные; списки обновляются при следующем опросе. Уже показанные или скачанные данные отозвать невозможно. Проверки повторяются в транзакции записи, в том числе перед обработкой повторного запроса. Журнал изменения ролей и доступа хранится в `access_history`.
